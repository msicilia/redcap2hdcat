CONFIRMED
  - Title: COMMISSION IMPLEMENTING REGULATION (EU) 2026/2098 of 18 September 2026 "laying down the minimum metadata elements
    and their characteristics to be provided by health data holders for dataset descriptions for the secondary use of
    electronic health data under Article 77(4) of Regulation (EU) 2025/327 establishing the European Health Data Space"
    (Text with EEA relevance). Legal basis: Art. 77(4), first sentence, of Regulation (EU) 2025/327.
  - OJ L series 2026/2098, 21.9.2026. ELI http://data.europa.eu/eli/reg_impl/2026/2098/oj. CELEX 32026R2098.
  - Art. 4: enters into force on the 20th day after publication (EUR-Lex: date of effect 11/10/2026, entry into force)
    and "shall apply from 26 March 2029" (EUR-Lex: 26/03/2029, application). No end date. Author: DG SANTE.
  - HealthDCAT-AP is binding for health data holders:
      Recital 5: "It is appropriate that the HealthDCAT-Application Profile (HealthDCAT-AP) is used as that metadata framework."
      Art. 1(1): the Regulation lays down the minimum elements "that health data holders are required to provide to health
        data access bodies pursuant to Article 60(3) ... as well as the metadata framework to be used".
      Art. 1(2): it also applies, "where relevant, to authorised participants in HealthData@EU".
      Art. 1(3): holders may add further elements voluntarily, using the same framework.
      Art. 2: the definitions in the HealthDCAT-AP referred to in Part A apply.
      Art. 3: the Part B elements must be expressed "by using the definitions, structure, cardinalities and controlled
        vocabularies set out in the HealthDCAT-AP referred to in Part A and C of the Annex". So HealthDCAT-AP CARDINALITIES
        are incorporated by reference, which matters wherever they conflict with the Part B conditions (see below).
  - Annex Part A footnote (1): "https://data.health.europa.eu/healthdcat-ap/releases/latest/." No release or version number
    appears anywhere in the act.
  - Annex Part B has 27 elements, in the same alphabetical order as the expected list and with the same names:
    Access rights, Applicable legislation, Code values, Coding system, Contact point, Conforms to, Custodian, Description,
    Distribution, Geographical coverage, Has personal data, Health data access body, Health data category, Health theme,
    Identifier, Is structured, Keyword, Language, Number of records, Number of unique individuals, Provenance, Publisher,
    Temporal coverage, Title, Type, Variables, Was generated by.
  - Part C: the only explicitly listed controlled vocabulary is "Health data category" = "The categories listed in
    Article 51(1), points (a) to (q) of Regulation (EU) 2025/327". Otherwise, where controlled vocabularies are required,
    "those defined in the HealthDCAT-AP ... shall be used". Part B also says: "Where applicable, controlled vocabularies
    defined in HealthDCAT-AP must be used."

DISCREPANCIES / PRECISIONS versus the expected list
  1. Numbering: Part B is an unnumbered two-column table (Property | Description). The numbers 1-27 are ours.
  2. Conditions are not a separate column; they are clauses inside each Description. Verbatim:
       Applicable legislation: "..., where such legal acts or legislation exists."           (matches)
       Code values: "..., where applicable."                                                 (matches)
       Coding system: "..., where applicable."                                               (matches)
       Geographical coverage: "..., where applicable."                                       (matches)
       Health data access body: "... where the dataset is subject to restricted or non-public access." (matches)
       Number of records: "..., where applicable."                                           (matches)
       Number of unique individuals: "... where the dataset contains personal data and where applicable." (matches)
       Temporal coverage: "..., where temporal information exists."                          (matches)
       Variables: "A structured description of the variables contained in the dataset, including, where applicable, the
         variable name, definition, data type, coding system or value domain."
         -> DIFFERS: "where applicable" qualifies the sub-items, not the element. The OJ text does not make
            Variables itself conditional. Treat it as unconditional, or flag it as an interpretation.
  3. Each element has a one-sentence definition (Description). Points worth noting for the mapping:
       Code values: "Identifies classification systems or controlled vocabularies reflected in the content of the dataset
         (e.g. disease classifications, procedure classifications)". This is close to HealthDCAT-AP's Coding system, not to
         its free-text code values (hasCodeValues, e.g. "U07.1").
       Coding system: "Identifies standardised coding schemes used to encode data elements within the dataset
         (e.g. ICD-10-CM, SNOMED-CT, DRGs)".
       Custodian: "...organisation responsible for holding, managing and maintaining the dataset over time (health data holder)."
       Distribution: "Provides a technical representation or format in which the dataset is made available for secondary use."
       Has personal data: "Indicates whether the dataset contains personal data within the meaning of Article 4, point (1),
         of Regulation (EU) 2016/679" (a yes/no notion).
       Health data category: "...categories of electronic health data ... listed in Article 51(1) of Regulation (EU) 2025/327."
       Is structured: "...organised according to a predefined schema or model that defines its variables, attributes or fields."
       Number of unique individuals: "Provides an ESTIMATED number of unique natural persons..."
       Publisher: "...entity making the dataset available, which may differ from the creator or custodian."
       Type: "...general category or nature of the dataset (e.g. registry, administrative dataset, research dataset, synthetic dataset)."
       Was generated by: "...activity or process through which the dataset was generated (e.g. registry, clinical study, administrative process)."
  4. Dates: all as expected (adopted 18.9.2026; OJ 21.9.2026; in force 11.10.2026; applies 26.3.2029).

Version ambiguity (important for the paper)
  The act cites only ".../releases/latest/". The Wayback Machine capture of the legacy "latest" URL
  (healthdataeu.pages.code.europa.eu/healthdcat-ap/releases/latest/) taken 2026-09-21 01:49 UTC, the OJ publication day,
  redirects to ../release-7/. On 2026-11-08 the official "latest" (data.health.europa.eu) redirects to release-8.
  There is no Wayback capture of the data.health.europa.eu "latest" URL, so what it pointed to on 21.9.2026 is unverified.
  Release 8's SHACL was still being changed on 2026-10-08 (commit cd7841fc), after adoption.

Release-8 obligations versus the 27 minimum elements (details: element_property_map.csv)
  - Two Part B conditions CONFLICT with Release 8 cardinalities, which Art. 3 incorporates:
      Applicable legislation is Mandatory 1..* at every access level.
      Health data access body is Mandatory 1..1 at every access level, PUBLIC included.
  - Many of the 27 "minimum" elements are only Recommended or Optional in Release 8, so the official SHACL does not
    enforce their presence (at most a Warning):
      Optional at every access level: Geographical coverage (dct:spatial), Was generated by (prov:wasGeneratedBy).
      Optional for PUBLIC and RESTRICTED: Provenance, Type, Language, Temporal coverage.
      Optional for PUBLIC and NON-PUBLIC: Conforms to (spec JSON; the shapes say otherwise).
      Recommended: Code values, Coding system, Custodian, Health theme, Number of records, Number of unique individuals,
        Has personal data, Publisher, Variables (hasVariables becomes Violation-mandatory when hasStructuredData=true),
        plus Contact point and Keyword for PUBLIC and RESTRICTED.
  - Release-8 mandatory property outside the 27: dcat:theme (1..*, and must include data-theme/HEAL). The
    non-public-only mandatory properties are all within the 27.
